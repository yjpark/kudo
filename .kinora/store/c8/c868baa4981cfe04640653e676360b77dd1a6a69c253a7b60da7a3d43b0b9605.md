# Spec — a context's repos declaration is a kino of its own

**Contract.** The repos a context spans are declared in one **repos kino**
under the context, separate from its head: one entry per repo, each a name,
the node it lives on, and its path there; a repo with a `.kinora/` ledger
mounts that ledger. The declaration is versioned by superseding, like the
head, and only a human (or a command acting for one) changes it — a submit
never does.

The node is the hub-qualified registry name, such as `edger::yolo`. Existing
unqualified names remain local aliases during explicit migration; nothing
rewrites them silently. A worker matches either its full local name or its
final `::` segment against `KUDO_NODE`, so this works offline. A direct launch
on a same-named peer is ambiguous until declarations are qualified.

A worker is started **in a repo by name**: the launcher looks the name up for
its node and starts the CLI in that path, bound to the context. A context
with no repo on a node cannot start a worker there by name.

**Chosen.** Its own kino. Repos change rarely and by decision; a head is
rewritten on every submit by a worker who has no reason to touch them. Keeping
them apart means no submit can drop a repo by accident, and the mounts table
has one version history a reader can audit. Qualified names prevent one peer's
repo from being read as another's.

**Rejected.** Repos as metadata on each head version (every submit must carry
them forward; one careless submit loses a mount). Repos inferred from where
workers happened to run (the cwd stopped identifying the work). Requiring a
hub lookup for local launch (the store and worker must work offline).

**Escape hatch.** A worker started outside any declared repo (plain
`kudo-shim worker <context>`) still works the context, from wherever it was
started. A future node protocol can supply a strict full identity instead of
final-segment matching.
