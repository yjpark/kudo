# Kudo — bundle 7 findings (13 Nov 2026, work stack at f356d94 / console 9921a2d)

First coding context on the work stack (a small Rust prototype, one repo, a
chain of sequential items, a second governed node `code` with bypass + strict
MCP). Six findings, worst first. Intent only; no code crosses.

## 1. Hub-connection leak in the console and the waker (bug, high)

- Measured: console and waker each at exactly 1024 fds (the soft limit); ~1000
  of each were ESTABLISHED TCP connections to the hub, not files. Console: 976
  hub connections 47 min after a restart (~20/min with a page open; +8 in 30 s
  after a fresh restart). Waker: +1 per 60 s pass, so it hits 1024 in ~17 h.
- Symptom when full: `context store: ledger io error: Too many open files
  (os error 24)` — the ledger files can no longer be opened. This is also the
  undiagnosed waker failure from 2 Nov ("Too many open files") that failed the
  shadow week.
- Cause (read in code, not verified inside vox): every operation dials a fresh
  `HubClient` and drops it, and dropping it does not close the socket —
  apparently the vox connection driver keeps it alive while the hub answers.
  Sites: `kudo-shim/src/main.rs` waker loop (`HubClient::dial` each pass);
  `kudo-console/src/server.rs` `hub()` (~:285, per screen read and per job
  call) and `nodes()` (~:352). `dial_lane` in `kudo-shim/src/hub.rs` keeps only
  the lane client; the connection handle is dropped after `open_lane()`.
- Fix direction: one long-lived `HubClient` per process (it already re-dials on
  transport failure via `redial`), and/or keep the connection handle and close
  it on drop. Add a test that N dials leave no open sockets. The hub on the Mac
  holds the other end of every leaked connection: check its fd count / launchd
  maxfiles too.
- Stopgap on the work stack: LimitNOFILE=65536 on console + waker, and a
  `kudo-work-restart.timer` restarting both every 12 h. Remove once fixed.

## 2. A "blocked" submit finishes the item (queue semantics)

Two workers on one context with a sequential chain: the second pulled item 2,
found item 1 not merged, submitted "blocked", then did the same to items 3 and
4 within a minute and ended queue-empty. There is no reopen; I had to
re-enqueue. The head's next_action still listed them (a good worker wrote it),
but a worker only pulls `ready`, so nothing picked them up.
Want: a submit can say `blocked-on <item|condition>` and the item returns to a
waiting state, ready again when the condition holds.

## 3. Item dependencies

Same incident from the other side: "ready only after item X is submitted" would
have kept the second worker idle instead of burning the chain. Items carried a
textual guard ("if X is not on main, submit blocked") as a workaround.

## 4. One repo per context; no per-item repo or worktree

Parallel alternative sketches (three designs at once) want one worker per
worktree. A context declares one repo per node, and any worker pulls any item,
so two workers share one checkout. Want: per-item repo/worktree, or a context
option "each lease gets its own worktree off main".

## 5. Approval-gated MCP writes for workers

Built a fail-closed PreToolUse hook for read-only MCP in worker sessions
(enforced when KUDO_LEASE is set; the first verb in a tool name decides; no verb
= deny). Live-tested under bypass: reads pass, a send is blocked by the hook,
and settings deny rules (git push, curl) still hold under bypass. With it,
STRICT_MCP becomes unnecessary for nodes that need to read. Want: instead of a
flat deny, park the write call in the console's approval queue (as governed
jobs already do) and let the hook wait for the verdict. Remaining hole is
egress: a Bash script can reach APIs directly through the credential-injecting
proxy, so read-only MCP is not read-only worker without an egress rule.

## 6. Console host error should name its setting

Reaching the console through a VM proxy name gave `the console does not answer
to "<host>"`. The fix is `KUDO_CONSOLE_HOSTS`, but the message doesn't say so.
Name the variable in the error.
